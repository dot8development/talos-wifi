WHAT "STUCK AT waitForUdevd" MEANS MECHANICALLY
  WaitForUdevd (internal/app/machined/pkg/runtime/v1alpha1/v1alpha1_sequencer_tasks.go:79)
  waits for the udevd service to reach StateEventUp (running AND healthy).
  udevd health (internal/app/machined/pkg/system/services/udevd.go:104-167) =
    `udevadm control --reload` -> `udevadm trigger --type=devices/--type=subsystems
    --action=add` -> `udevadm settle --timeout=50` (+ ExtraSettleTime).
  "udevd process visible but never healthy" == the settle queue never drains
  (or reload/trigger fails every round). That also explains everything else:
  no NIC modules get loaded by udevd's kmod builtin -> dashboard "(none)";
  USB/ISO block device never appears -> VolumeManager platform/metal-iso/config
  waiting -> missing -> closed. One root cause, all symptoms downstream.

  Corollary: the culprit must act on the udev event queue BEFORE any wifi
  controller ever runs (see clearance of suspect area 2 below).

AREA-BY-AREA FINDINGS
--------------------------------------------------------------------------------

[1] hack/udevd/90-selinux.rules rfkill SECLABEL line  -> LARGELY CLEARED
  The only udev-visible change on the branch:
    KERNEL=="rfkill",SECLABEL{selinux}="system_u:object_r:rfkill_device_t:s0"
  (added in 90fc58313, inserted before the existing "zero" line - syntactically
  fine; upstream file already uses SECLABEL for tpm/tpmrm/watchdog/null).

  a) Type exists in the shipped policy. `strings internal/pkg/selinux/policy/
     policy.33` contains rfkill_device_t (and wpa_supplicant_{t,exec_t,run_t}).
     The machined binary embeds the COMMITTED policy.33 (Dockerfile `base`
     stage copies ./internal as-is; the `selinux` secilc stage feeds only the
     `generate` stage / `make generate`). So the udev context resolves in the
     loaded policy; setfilecon will not get EINVAL.
  b) systemd-udevd v257 semantics: SECLABEL failure in udev-node permission
     application is log-and-continue (log_device_error_errno path), it does not
     fail or retry the event, and cannot wedge a worker. Worst case = one error
     line per event.
  c) THE KEY QEMU FACT: the rule matches only the rfkill MISC device
     (/dev/rfkill), not rfkill0/rfkill1 class devices (those have no devnode,
     SECLABEL is a devnode operation). With the fork kernel's CONFIG_RFKILL=y
     (builtin), rfkill_init() registers /dev/rfkill unconditionally at boot on
     EVERY machine - including QEMU. The QEMU run therefore already exercised
     this exact rule+policy combination and passed. The premise "QEMU has no
     rfkill" is only true for rfkill class devices, which this rule ignores.
  Residual risk (small, cheap to kill): there is a commit window
  90fc58313..b71ff255e where the rule references rfkill_device_t but the
  committed policy.33 did not yet contain it. An ISO built inside that window
  would log SECLABEL EINVAL on /dev/rfkill (still non-fatal per (b)). Verify
  the QEMU-tested ISO and the laptop-flashed ISO are the same sha256 and built
  from 2ef37f0df.

[2] Wifi controllers / wpa_supplicant service  -> CLEARED as boot blocker
  (internal/app/machined/pkg/controllers/network/wifi_{config,service,status}.go,
   watch/nl80211.go, system/services/wpa_supplicant.go,
   runtime/v1alpha2/v1alpha2_controller.go + v1alpha2_state.go)

  - WifiStatusController.Run first blocks in runtime.WaitForDevicesReady()
    (controllers/runtime/utils.go:23), which waits for runtime.DevicesStatus
    .Ready - and DevicesStatus only becomes Ready AFTER udevd settles. During
    the observed hang this controller is parked on r.EventCh(); it cannot be
    cause, only victim (circular the wrong way round).
  - nl80211-family-missing path (iwlwifi blacklisted, cfg80211 never loads):
    watch.NewNL80211 -> conn.GetFamily("nl80211") fails -> controller logs
    debug and `return nil`. In cosi runtime v1.16.2 rruntime/run.go:26-28,
    a controller whose Run returns nil is NOT restarted - the adapter's loop
    does `if err == nil { return }`. There is no tight error/restart loop, no
    backoff churn, no runtime starvation. (Confirmed empirically too: the QEMU
    boot with e1000-only hardware took exactly this path and reached
    maintenance mode.)
  - The wifi.Client dial happens once per Run invocation, not per iteration;
    an error inside reconcile() returns from Run -> single backoff restart ->
    re-blocks in WaitForDevicesReady. Sane.
  - WifiServiceController is purely event-driven on WifiSpec+LinkStatus; with
    no machine config there are no WifiSpecs, reconcile() desired set is empty,
    it idles on EventCh. It never touches udevd, never runs at "Booting" stage.
  - WifiConfigController waits on MachineConfig; inert pre-config.
  - wpa_supplicant service is only Loaded/Started by WifiServiceController
    (never at boot); Condition waits for its config file; cannot block the
    sequencer.
  - Registration diffs (v1alpha2_controller.go +5, v1alpha2_state.go +2) are
    plain additions; system.Services(ctrl.v1alpha1Runtime) uses the same
    runtime singleton pattern as the existing UdevServiceController wiring.

  Non-blocking BUG found here anyway: because return-nil == permanent stop,
  WifiStatusController permanently disables itself on machines where wifi
  hardware/extension appears after first devices-ready (or where cfg80211
  loads late). Should retry/watch instead. Not related to the hang.

[4] Dockerfile / Makefile  -> CLEARED for the hang; one real side bug (arm64)
  - pkg-wpa-supplicant image content verified from
    /Users/tom/Documents/Projects/talos-pkgs/wpa-supplicant/pkg.yaml:
    variant scratch; installs ONLY /usr/bin/{wpa_supplicant,wpa_cli,

TOP 3 SUSPECTS (ranked, with mechanism + cheap disconfirming test)
--------------------------------------------------------------------------------

#1  THE FORK KERNEL BUILD (pkgs 6.18.46 + wireless config delta), not the
    talos repo diff.  Confidence this is where the bug lives: high, by
    elimination - every userland/rootfs change on the branch is either
    exercised identically in QEMU (same ISO boots: same policy, same udev
    rules, same wpa binary, /dev/rfkill present in QEMU too) or provably
    parked until after udevd settles. The only branch component that behaves
    differently on real HP hardware is the kernel: CONFIG_RFKILL=y,
    CONFIG_WLAN=y, LEDS/rfkill wiring now compiled into builtin ACPI/platform
    driver paths that probe EliteBook hardware (WMI, EC, hotkeys) during the
    udev trigger storm, plus the fact that it is a different kernel BUILD
    (fork registry) than the upstream-published 6.18.46. A single device whose
    uevent/probe blocks >50s on every `udevadm trigger` retry keeps settle
    timing out forever == exactly this symptom.
    DISCONFIRM (cheap, decisive bisect of kernel vs rootfs):
      a) Build the branch-wifi ISO with upstream kernel only:
         `make iso PKG_KERNEL=ghcr.io/siderolabs/kernel:<upstream tag>`
         (keep wpa/regdb overrides; wifi won't function - irrelevant).
         Boots on laptop => kernel delta guilty.
      b) Converse: vanilla main-HEAD rootfs + fork kernel => hangs => confirmed.
      (The running vanilla-main A/B answers only half of this matrix - vanilla
      main uses the upstream kernel, so "vanilla works" does NOT yet acquit
      our rootfs until (a) is run.)

#2  udev rfkill SECLABEL rule + policy window / artifact mismatch.
    Mechanism would be: udev worker failing or looping while labeling
    /dev/rfkill. Code analysis says non-fatal (udevd logs and continues) and
    rfkill_device_t IS in the shipped policy, and QEMU already exercised the
    rule (/dev/rfkill exists there too, RFKILL=y is builtin) - so this is a
    weak suspect kept at #2 only because it is the sole udev-visible change
    and dirt cheap to eliminate.
    DISCONFIRM: rebuild ISO with the one rfkill line deleted from
    hack/udevd/90-selinux.rules; boot laptop. Also sha256-compare the ISO file
    QEMU booted vs the file flashed to USB (rules commit 90fc58313 and policy
    regen b71ff255e are 30 min apart - make sure both tests used a
    post-b71ff255e artifact), and re-flash to rule out a bad USB write
    (a corrupted squashfs on USB reproduces "modules never load" symptoms
    while QEMU boots the intact file perfectly).

#3  Wifi controllers starving/blocking machined - CLEARED, listed to close it
    out explicitly: WifiStatusController blocks in WaitForDevicesReady (which
    only unblocks AFTER udevd settles - wrong direction to cause this);
    nl80211-missing => Run returns nil => cosi v1.16.2 permanently retires the
    controller (rruntime/run.go: `if err == nil { return }`) - no restart
    loop, no backoff churn; WifiService/WifiConfig idle without machine
    config; wpa_supplicant service never loaded at boot. QEMU (e1000, no
    nl80211) walked these exact paths to maintenance mode.
    DISCONFIRM (if paranoid): build with the three controller registrations
    removed from v1alpha2_controller.go; boot laptop. Expected: still hangs.

BEST SINGLE DIAGNOSTIC regardless of suspect: boot the laptop with extra args
`udev.log_level=debug` (and optionally `udev.event_timeout=20`), then read the
udevd service log from the dashboard log pane. The stuck/killed event will name
the exact device/driver; `udevadm settle` timeout messages will confirm the
health-check theory within one boot.

    reconcile - log spam once wifi configs exist.  [wifi_service.go:111-115]

    only exists in policy.33 as of b71ff255e; intermediate builds emit
    SECLABEL errors on /dev/rfkill. Squash rule+policy regen in one commit
    when upstreaming.
